NetProbe 3.3.3 — no false DPI conflicts, no leftover kill switch rules
## Fix: false "DPI conflict" on emergency VPN → DPI switch
- When NetProbe switched to DPI (VPN not responding) while winws was already running — e.g. DPI turned on manually or in ROUTE mode — the conflict check treated NetProbe's **own** `winws.exe` as a foreign one, killed it and started it again.
- Effect: a short gap with no DPI bypass on every switch, `TLS handshake failed: Connection was reset` in the log, `DPI conflict: winws.exe … — stopping it` warnings, and sometimes an extra "winws.exe exited" restart that used up the restart limit.
- Now the conflict check skips NetProbe's own winws; only real foreign winws / zapret / GoodbyeDPI services are stopped.

## Fix: kill switch rules left after a crash or update
- If NetProbe was closed abnormally (crash, Task Manager) or updated while the kill switch was active, its "NetProbe KillSwitch" firewall rules stayed in Windows and kept blocking Strict VPN apps (e.g. `ERR_NETWORK_ACCESS_DENIED`) even after restart.
- NetProbe now removes leftover kill switch rules on start, and releases them when VPN comes back or when you disconnect.
